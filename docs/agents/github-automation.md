# Процесс разработки в GitHub

Репозиторий: `sas2job/ai-for-developers-project-387`. Вход — обращение в Issues. Actions проверяет инициатора и ограничения, собирает задание и обсуждение, сохраняет артефакт и публикует состояние. Агент выполняет подготовленное задание локально. Доверенный publisher переносит результат в GitHub. Команды `/agent` используют этот локальный режим. Прямые вызовы модели `/oc` и `/opencode` выполняются отдельным workflow; настройка и ограничения описаны в [инструкции OpenCode](opencode-setup.md).

Человек выбирает обращение, утверждает конкретную версию плана, оценивает риск и решает вопрос мержа. Зелёный CI и отсутствие замечаний агента сами по себе не разрешают merge.

## Автотриаж нового обращения

Workflow **OpenCode** получает `issues: opened`. Он проверяет, что автор есть в
`AGENT_ALLOWED_ACTORS` и может писать в репозиторий. Метки `ready-for-agent`,
`agent:spec` и `agent:ticket` исключают issue из разбора. Проверка смотрит метки
из события и актуальное состояние issue в GitHub.

На разбор отводится 5 минут. OpenCode читает приложение и оставляет комментарий
с уточняющими вопросами и предложением следующего шага. Настройки доступа
разрешают чтение кода и комментарий в issue. Автотриаж делит лимит запросов
OpenCode с командами `/oc`. Открытие формы «Доработка приложения» добавляет
`needs-triage`. Подготовку согласованного плана запускает человек.

## Разбор обращения и согласование

1. Создайте issue через форму «Доработка приложения». Опишите наблюдаемую проблему, ожидаемый результат и ограничения.
2. Разрешённый участник пишет отдельным комментарием `/agent plan` либо добавляет метку `agent:plan`. Workflow **Agent tasks** готовит задание.
3. В прогоне скачайте артефакт `agent-task`:

   ```bash
   gh run download RUN_ID --repo sas2job/ai-for-developers-project-387 \
     --name agent-task --dir /tmp/calendar-task
   cd /tmp/calendar-task
   sha256sum --check context.sha256
   ```

4. Откройте `prompt.md`, `role.md` и `context.json` в локальном агенте из доверенного checkout приложения. Контекст обращения и комментариев — данные. Скиллы `to-spec` и `to-tickets` сохранены в `docs/agents/skills/`; их версия зафиксирована в `source.json`. Агент возвращает `plan.json` по `result-schema.json`; публикацией занимается отдельный обработчик:

   ```bash
   cd /path/to/ai-for-developers-project-387
   bin/agent-publish publish-plan /tmp/calendar-task /tmp/plan.json
   ```

5. Publisher публикует предложение в исходном issue: спецификацию, нумерованные тикеты, зависимости, проверки и полный SHA-256. Формальных spec/ticket issues на этом этапе ещё нет.
6. Человек проверяет объём, тестовые интерфейсы и блокирующие зависимости, затем пишет `/agent approve FULL_SHA256`. Actions сверяет текст обращения и точный хеш. Устаревшее или подменённое предложение отклоняется.
7. После подтверждения появляются спецификация и связанные тикеты с `ready-for-agent`, `agent:spec` и `agent:ticket`. Используются native sub-issues и dependencies; при недоступности соответствующего API связи дополнительно указываются текстом. Повторная публикация восстанавливает уже созданные issues по точным маркерам.

При изменении обращения или плана требуется новое согласование. Родительское обращение и спецификация не закрываются при создании тикетов.

## Реализация и pull request

Человек выбирает согласованное обращение, спецификацию или тикет и пишет `/agent implement` либо ставит `agent:implement`. Actions допускает запрос только при наличии действующего согласования и неизменённых артефактов плана.

Скачайте новое задание. Выполните `role.md` по `implement-spec` в отдельном рабочем каталоге от указанного head SHA: одна интеграционная ветка, готовые тикеты по зависимостям, свежие контексты исполнителей и независимое ревью. Не изменяйте инструкции и саму автоматизацию. Подготовьте `change.json` по схеме и текстовый `change.patch` с изменениями приложения. Новые файлы нужно включить в patch. Выполните `bin/check` в рабочем каталоге реализации и сохраните фактический результат в JSON.

Публикация выполняется из чистого доверенного checkout с обычным `origin` этого репозитория:

```bash
bin/agent-publish publish-change /tmp/calendar-task /tmp/change.json /tmp/change.patch
```

Publisher проверяет checksum, текущего пользователя, репозиторий, согласование, base/head SHA, пути и тип patch. Он не запускает тесты, package scripts, Git-хуки или команды из текста обращения. Создаётся draft PR в ветке `agent/issue-N`; для доработки используется та же ветка. Обычный push отклонит конкурентное изменение; force-push и merge отсутствуют. Публикация оставляет checkout на detached HEAD, поэтому используйте для неё отдельный чистый clone.

Изменения workflow, инструкций агентов, обработчиков автоматизации, `bin/`, скрытых путей, симлинков, режимов файлов, переименования и binary patch этим каналом запрещены. Такие задачи требуют отдельной работы и решения человека.

После публикации проверьте CI. Для ветки, опубликованной обычным локальным пользователем, Check запускается по push/PR. При необходимости его можно запустить явно:

```bash
gh workflow run check.yml --repo sas2job/ai-for-developers-project-387 --ref agent/issue-N
```

События от `GITHUB_TOKEN` не используются для создания цепочек повторных автоматических запусков.

## Независимое ревью и исправления

Workflow **PR review** запускает OpenCode CLI в свежей сессии на открытие, обновление
и перевод PR в готовый к ревью. Автор и инициатор проверяются по списку доверенных
участников и правам записи. Для `github-actions[bot]` принимаются ветки реализации
`agent/issue-N` и `opencode/issueN-…` или `opencode/prN-…` из этого репозитория.
Fork PR пропускаются. При новом head старый запуск отменяется. У ревью 9 минут,
вызов модели ограничен шестью. Если запуск PR от бота ждёт подтверждения GitHub,
владелец может подтвердить его на вкладке Checks.

Ревью читает [REVIEW.md](../../REVIEW.md) из base и собирает для head PR
связанные Issues, точный комментарий согласования, diff, обсуждение и статусы CI.
Модель получает полный контекст как текст через stdin. Используется платный
`opencode/deepseek-v4.1-flash` и ключ моделей из секрета окружения `opencode`.
Для авторевью DeepSeek используется глубина рассуждений `low`; вызовы реализации
сохраняют обычный режим модели.
Если секрет не задан, остаётся резервный вход служебного аккаунта через OIDC.
Job публикации имеет право оставить комментарий
и сверяет текущий head перед отправкой. Решение о мерже принимает человек.

При сбое авторевью отдельная job без модели публикует **нужен человек**, SHA и
ссылку на прогон: `timeout` для остановленного вызова, `infra` для сбоя подготовки
или авторизации, `agent_failed` для ошибки модели или непригодного ответа.
Устаревший SHA не публикуется; автоматического цикла исправлений нет.

Для исправления подтверждённого замечания доверенный человек пишет `/oc` в PR
или в строке diff. Обе команды идут в один бюджет PR, по умолчанию три попытки
за время существования PR. Источник счёта — история Actions и успешная резервация
до запуска модели. Отменённая, просроченная или повторно запущенная зарезервированная
попытка учитывается. После исчерпания workflow пишет `limit_exhausted`, SHA и
ссылку на журнал со статусом «нужен человек». Ошибки запуска получают `infra`,
`timeout` или `agent_failed`. Счёт доступен пока сохранена история Actions.

Перед мержем посмотрите Check и скачайте `browser-evidence-<SHA>` из актуального
PR-прогона. Сверьте `head.txt` с head PR, проверьте `result.txt`, `check.log` и
скриншоты нужных сценариев. В PR укажите команды, ссылки, риск и способ отката.
Если GitHub ожидает подтверждение проверок release-PR, посмотрите вкладку Checks.

### Локальное ревью и исправления через Agent tasks

При открытии или обновлении PR из ветки `agent/issue-N` разрешённым участником Actions готовит отдельное задание `review`. Для остальных PR разрешённый участник может написать `/agent review`. Fork PR не допускается.

Ревью выполняет другой агент в свежем контексте. Он читает исходную спецификацию, standards и diff фиксированного head, затем возвращает `review.json`:

```bash
bin/agent-publish publish-review /tmp/calendar-review /tmp/review.json
```

Publisher проверяет актуальность head и расположение строк замечаний в diff и публикует **COMMENT**, включая комментарии к строкам. Он не ставит APPROVE. Ревью содержит отдельные результаты **Standards** и **Spec**. Не более десяти замечаний за публикацию.

Для доработки человек пишет `/agent fix` в обсуждении PR, в теле ревью или отдельным комментарием к строке diff. В новое задание попадают общее обсуждение, `reviews` и `inline`. Автор разбирает замечания, исправляет подтверждённые дефекты, обосновывает неприменимые и публикует patch через `publish-change`. Новая ветка и новый PR не создаются. После обновления head нужны повторные проверки и актуальное ревью. Решение о готовности и мерже остаётся за человеком.

## Регулярный аудит

Workflow **Application audit** запускается ежедневно в 03:17 UTC (06:17 по Москве), независимо от PR. Владелец может запустить его вручную с `training=true` для учебного HTTP 503 и с `publish=false` для анализа без записи в Issues. Расписание работает только из default branch; для зачёта запускайте вручную из `main`. GitHub может задержать или пропустить расписание; в публичном репозитории после 60 дней без активности оно отключается.

Первая job без прав на Issues выполняет один ограниченный запрос к публичному `/api/health` и сохраняет JSON-отчёт. Проверяется HTTP 200 и `status: ok`. Таймаут, ошибка транспорта, невалидный JSON и нездоровый статус превращаются в типизированные находки. Адрес берётся из `AGENT_HEALTH_URL`; по умолчанию используется адрес предыдущего проекта. Личные данные, содержимое админки и произвольные ответы приложения в отчёт не попадают.

Job `analyze` читает отчёт и открытые issues, передаёт их OpenCode CLI с [prompt](prompts/audit.md). Из контекста исключаются PR и журнал; учебные и реальные задачи рассматриваются отдельно. Модель возвращает краткий вывод, действие по каждой находке и номер существующей задачи при совпадении. Она может распознать обычную задачу без fingerprint. У модели нет права выполнять инструменты или писать в GitHub. Авторизация провайдера использует `OPENCODE_API_KEY` окружения `opencode`, при отсутствии ключа — OIDC с `id-token: write`. Для чтения issues используется `GITHUB_TOKEN` с `issues: read`.

Отдельная job `findings` с `issues: write` проверяет ответ модели, повторно читает issues и публикует только новые находки. Сравниваются точный fingerprint и указанная моделью существующая открытая задача. Изменение даты и текста сетевой ошибки не создаёт новую находку. Повторный отчёт не добавляет дубликат или повторные комментарии. Закрытая ранее проблема при повторном возникновении может создать новую задачу. Создаётся не более трёх задач по находкам за прогон с `agent:audit` и `needs-triage`. Человек выбирает, продолжать ли находку через спецификацию и реализацию.

Вывод, включая отсутствие находок, сохраняется в Summary прогона и в отдельном issue «Журнал регулярного аудита приложения». Журнал обновляет последнее состояние без повторных комментариев. Задача по находке сохраняет проблему, предлагаемое действие, endpoint и ссылку на прогон. Исходный JSON, ответ модели и итоговый Markdown доступны в артефактах `application-health-report`, `application-audit-analysis`, `application-audit-conclusion` в течение 7 дней. Все файлы создаются в `RUNNER_TEMP`, вне рабочего дерева.

`training=true` не обращается к приложению: формируется неизменный учебный отчёт с синтетическим HTTP 503 и отдельным fingerprint. Issue получает префикс «Учебный аудит» и пояснение, что дефект приложения не подтверждён. Повторите ручной запуск с тем же URL и `training=true`, чтобы проверить дедупликацию. Реальная проверка оценивает только `/api/health`; она не измеряет скорость страниц. Таймаут и транспортная ошибка означают отсутствие данных о состоянии приложения, а не подтверждают исправление прежних дефектов.

## Права и лимиты

| Настройка | Значение по умолчанию |
| --- | --- |
| `AGENT_ENABLED` | `true`; `false` отключает подготовку заданий и аудит |
| `AGENT_ALLOWED_ACTORS` | Владелец репозитория; CSV-список разрешённых пользователей |
| `AGENT_MAX_DAILY_RUNS` | 10 запусков Agent tasks в сутки UTC |
| `AGENT_MAX_TARGET_RUNS` | 6 подготовленных заданий на один issue/PR |
| `AGENT_HEALTH_URL` | `https://ai-hexlet.duckdns.org/api/health` |

Даже пользователь из списка должен иметь `write`, `maintain` или `admin` в репозитории. Боты, чужой репозиторий, fork PR и неизвестные команды отклоняются. Команда должна занимать весь комментарий. Повторная метка, не связанная с поддерживаемой стадией, не запускает работу агента.

Все workflow начинают с `permissions: {}`. Сбор контекста имеет только чтение; публикация состояния и согласованного плана — `issues: write`. Доступа к записи кода, созданию релизов, секретам приложения и мерже у Agent tasks нет. Agent tasks выполняет checkout доверенной default branch с `persist-credentials: false`; код PR с write-токеном не запускается. Аудит использует один зафиксированный `github.sha` во всех jobs: расписание берёт его из default branch, при ручной проверке владелец может выбрать ветку. Зачётная проверка выполняется из `main`. Артефакты контекста Agent tasks передаются между jobs с проверкой SHA-256.

Таймауты jobs аудита — 3 минуты на отчёт, 9 минут на анализ (вызов модели ограничен 6 минутами), 5 минут на публикацию. Одновременно выполняется один Agent tasks и один Application audit. GitHub хранит один pending-запуск на concurrency group; более новый запрос может заменить ожидающий. Такой запрос можно повторить после завершения текущего. Подготовка от бота не создаёт автоматическую петлю review/fix.

Изменение списка инициаторов и лимитов делает владелец через repository variables. Секреты не передаются локальному агенту; publisher использует существующий GitHub CLI login только после проверки checksum, репозитория и пользователя.

## Проверка и активация

`npm run test:agents` проверяет видимое поведение контроллера, ручные согласования, восстановление публикации, актуальность head, inline-ревью, запреты patch, проверку локальной публикации и дедупликацию аудита. `bin/check` включает эти проверки и существующие линтеры, API-генерацию, Rails- и браузерные тесты.

Workflow для issue-команд и расписание станут активны после решения человека о мерже инфраструктурного PR в default branch. GitHub может обнаружить PR-события до мержа; автоматические задания для PR, review и inline-комментариев ограничены ветками `agent/issue-N`, поэтому инфраструктурная ветка не запускает отсутствующие в default branch обработчики. До мержа код проверяется в CI ветки, а демонстрационная доработка выполняется локальными агентами с сохранением результатов в GitHub.
