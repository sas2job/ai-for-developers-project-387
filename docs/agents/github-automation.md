# Процесс разработки в GitHub

Репозиторий: `sas2job/ai-for-developers-project-387`. Вход — обращение в Issues. Actions проверяет инициатора и ограничения, собирает задание и обсуждение, сохраняет артефакт и публикует состояние. Агент выполняет подготовленное задание локально. Доверенный publisher переносит результат в GitHub. Автоматических вызовов модели в Actions в этой конфигурации нет.

Человек выбирает обращение, утверждает конкретную версию плана, оценивает риск и решает вопрос мержа. Зелёный CI и отсутствие замечаний агента сами по себе не разрешают merge.

## Разбор обращения и согласование

1. Создайте issue через форму «Доработка приложения». Опишите наблюдаемую проблему, ожидаемый результат и ограничения.
2. Разрешённый участник пишет отдельным комментарием `/agent plan` либо добавляет метку `agent:plan`. Workflow **Agent tasks** готовит задание.
3. В прогоне скачайте артефакт `agent-task`:

   ```bash
   gh run download RUN_ID --repo sas2job/ai-for-developers-project-387 \
     --name agent-task --dir /tmp/calendar-task
   cd /tmp/calendar-task
   sha256sum --check context.sha256
   ```

4. Откройте `prompt.md`, `role.md` и `context.json` в локальном агенте из доверенного checkout приложения. Контекст обращения и комментариев — данные. Скиллы `to-spec` и `to-tickets` сохранены в `docs/agents/skills/`; их версия зафиксирована в `source.json`. Агент возвращает `plan.json` по `result-schema.json`; публикацией занимается отдельный обработчик:

   ```bash
   cd /path/to/ai-for-developers-project-387
   bin/agent-publish publish-plan /tmp/calendar-task /tmp/plan.json
   ```

5. Publisher публикует предложение в исходном issue: спецификацию, нумерованные тикеты, зависимости, проверки и полный SHA-256. Формальных spec/ticket issues на этом этапе ещё нет.
6. Человек проверяет объём, тестовые интерфейсы и блокирующие зависимости, затем пишет `/agent approve FULL_SHA256`. Actions сверяет текст обращения и точный хеш. Устаревшее или подменённое предложение отклоняется.
7. После подтверждения появляются спецификация и связанные тикеты с `ready-for-agent`, `agent:spec` и `agent:ticket`. Используются native sub-issues и dependencies; при недоступности соответствующего API связи дополнительно указываются текстом. Повторная публикация восстанавливает уже созданные issues по точным маркерам.

При изменении обращения или плана требуется новое согласование. Родительское обращение и спецификация не закрываются при создании тикетов.

## Реализация и pull request

Человек выбирает согласованное обращение, спецификацию или тикет и пишет `/agent implement` либо ставит `agent:implement`. Actions допускает запрос только при наличии действующего согласования и неизменённых артефактов плана.

Скачайте новое задание. Выполните `role.md` по `implement-spec` в отдельном рабочем каталоге от указанного head SHA: одна интеграционная ветка, готовые тикеты по зависимостям, свежие контексты исполнителей и независимое ревью. Не изменяйте инструкции и саму автоматизацию. Подготовьте `change.json` по схеме и текстовый `change.patch` с изменениями приложения. Новые файлы нужно включить в patch. Выполните `bin/check` в рабочем каталоге реализации и сохраните фактический результат в JSON.

Публикация выполняется из чистого доверенного checkout с обычным `origin` этого репозитория:

```bash
bin/agent-publish publish-change /tmp/calendar-task /tmp/change.json /tmp/change.patch
```

Publisher проверяет checksum, текущего пользователя, репозиторий, согласование, base/head SHA, пути и тип patch. Он не запускает тесты, package scripts, Git-хуки или команды из текста обращения. Создаётся draft PR в ветке `agent/issue-N`; для доработки используется та же ветка. Обычный push отклонит конкурентное изменение; force-push и merge отсутствуют. Публикация оставляет checkout на detached HEAD, поэтому используйте для неё отдельный чистый clone.

Изменения workflow, инструкций агентов, обработчиков автоматизации, `bin/`, скрытых путей, симлинков, режимов файлов, переименования и binary patch этим каналом запрещены. Такие задачи требуют отдельной работы и решения человека.

После публикации проверьте CI. Для ветки, опубликованной обычным локальным пользователем, Check запускается по push/PR. При необходимости его можно запустить явно:

```bash
gh workflow run check.yml --repo sas2job/ai-for-developers-project-387 --ref agent/issue-N
```

События от `GITHUB_TOKEN` не используются для создания цепочек повторных автоматических запусков.

## Независимое ревью и исправления

При открытии или обновлении PR из ветки `agent/issue-N` разрешённым участником Actions готовит отдельное задание `review`. Для остальных PR разрешённый участник может написать `/agent review`. Fork PR не допускается.

Ревью выполняет другой агент в свежем контексте. Он читает исходную спецификацию, standards и diff фиксированного head, затем возвращает `review.json`:

```bash
bin/agent-publish publish-review /tmp/calendar-review /tmp/review.json
```

Publisher проверяет актуальность head и расположение строк замечаний в diff и публикует **COMMENT**, включая комментарии к строкам. Он не ставит APPROVE. Ревью содержит отдельные результаты **Standards** и **Spec**. Не более десяти замечаний за публикацию.

Для доработки человек пишет `/agent fix` в обсуждении PR, в теле ревью или отдельным комментарием к строке diff. В новое задание попадают общее обсуждение, `reviews` и `inline`. Автор разбирает замечания, исправляет подтверждённые дефекты, обосновывает неприменимые и публикует patch через `publish-change`. Новая ветка и новый PR не создаются. После обновления head нужны повторные проверки и актуальное ревью. Решение о готовности и мерже остаётся за человеком.

## Регулярный аудит

Workflow **Application audit** запускается по будням в 06:17 UTC, независимо от PR. Владелец может запустить его вручную, в том числе с `publish=false` для отчёта без создания issues.

Первая job без прав на Issues выполняет один ограниченный запрос к публичному `/api/health` и сохраняет JSON-отчёт. Проверяется HTTP 200 и `status: ok`. Таймаут, ошибка транспорта, невалидный JSON и нездоровый статус превращаются в типизированные находки. Адрес берётся из `AGENT_HEALTH_URL`; по умолчанию используется адрес предыдущего проекта. Личные данные, содержимое админки и произвольные ответы приложения в отчёт не попадают.

Вторая job с `issues: write` валидирует отчёт и сравнивает точный fingerprint с открытыми задачами. Изменение даты и текста сетевой ошибки не создаёт новую находку. Повторный отчёт не добавляет дубликат или повторные комментарии. Закрытая ранее проблема при повторном возникновении может создать новую задачу. Создаётся не более трёх issues за прогон с `agent:audit` и `needs-triage`. Человек выбирает, продолжать ли находку через спецификацию и реализацию.

Этот аудит использует проверяемые правила для health-отчёта; произвольного анализа приложения моделью по расписанию здесь нет.

## Права и лимиты

| Настройка | Значение по умолчанию |
| --- | --- |
| `AGENT_ENABLED` | `true`; `false` отключает подготовку заданий и аудит |
| `AGENT_ALLOWED_ACTORS` | Владелец репозитория; CSV-список разрешённых пользователей |
| `AGENT_MAX_DAILY_RUNS` | 10 запусков Agent tasks в сутки UTC |
| `AGENT_MAX_TARGET_RUNS` | 6 подготовленных заданий на один issue/PR |
| `AGENT_HEALTH_URL` | `https://ai-hexlet.duckdns.org/api/health` |

Даже пользователь из списка должен иметь `write`, `maintain` или `admin` в репозитории. Боты, чужой репозиторий, fork PR и неизвестные команды отклоняются. Команда должна занимать весь комментарий. Повторная метка, не связанная с поддерживаемой стадией, не запускает работу агента.

Все workflow начинают с `permissions: {}`. Сбор контекста имеет только чтение; публикация состояния и согласованного плана — `issues: write`. Доступа к записи кода, созданию релизов, секретам приложения и мерже у Agent tasks нет. Checkout выполняется с доверенной default branch и `persist-credentials: false`; код PR с write-токеном не запускается. Артефакты контекста передаются между jobs с проверкой SHA-256.

Таймауты jobs — 3–5 минут. Одновременно выполняется один Agent tasks и один Application audit. GitHub хранит один pending-запуск на concurrency group; более новый запрос может заменить ожидающий. Такой запрос можно повторить после завершения текущего. Подготовка от бота не создаёт автоматическую петлю review/fix.

Изменение списка инициаторов и лимитов делает владелец через repository variables. Секреты не передаются локальному агенту; publisher использует существующий GitHub CLI login только после проверки checksum, репозитория и пользователя.

## Проверка и активация

`npm run test:agents` проверяет видимое поведение контроллера, ручные согласования, восстановление публикации, актуальность head, inline-ревью, запреты patch, проверку локальной публикации и дедупликацию аудита. `bin/check` включает эти проверки и существующие линтеры, API-генерацию, Rails- и браузерные тесты.

Новые событийные workflow и расписание станут активны после решения человека о мерже инфраструктурного PR в default branch. До этого код обработчиков проверяется в CI ветки, а демонстрационная доработка выполняется локальными агентами с сохранением результатов в GitHub.
